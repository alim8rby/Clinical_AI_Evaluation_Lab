# V4.5 Audit — Evaluation and Failure Runtime

## Status

V4.5 is complete and frozen at the application-domain level.

## Verified by source inspection

- Experiments can be created and persisted through the SQL repository.
- Benchmark questions execute through the application runtime.
- Runs transition from running to completed or failed.
- Frozen V2 retrieval, answer, grounding, and reliability evaluators are reused.
- V3 failure classification and persistence are reused through the SQL failure adapter.
- Answers, citations, evaluations, and failures have relational persistence adapters.
- Experiment comparisons aggregate persisted evaluation metrics and expose transparent deltas.
- Experiment reports expose configuration, sample count, aggregate metrics, and persisted failures.
- Run evidence can be queried from persisted citations and their source chunks.
- API routes remain orchestration/adaptation boundaries rather than owning evaluation logic.
- Ollama remains provider-injected and provider-specific types do not enter the frozen domain contracts.

## Deliberate limitations

- This phase does not claim local runtime or Ollama execution; verification is repository/source-contract inspection.
- Retrieval scores are not persisted yet, so the run-evidence endpoint returns score null rather than inventing a value.
- Run evidence currently reconstructs cited chunks; a future persistence pass can store the full ranked evidence set and scores.
- Token counts and cost remain nullable until provider telemetry is wired in V4.6.
- Report aggregation is persistence-backed but does not replace the richer V2 in-memory Markdown renderer.
- PostgreSQL is the production target; local SQLite remains available for development.
- The controlled corpus remains the V2 compact depression corpus.

## Compatibility

V1 RAG, V2 evaluation, and V3 failure contracts are unchanged. V4.5 only adds application orchestration and persistence adapters around them.

## Freeze rule

Changes to failure semantics, evaluation metrics, benchmark semantics, or RAG contracts require an explicit versioned design decision rather than being introduced as incidental V4 infrastructure work.
