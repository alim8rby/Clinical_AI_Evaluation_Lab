# V5.5 — Experiment Engine

## Goal

Turn the V5.3 retrieval and V5.4 generation research layers into reproducible batch experiments.

V5.5 adds:

- batch execution over a fixed question set
- deterministic experiment configuration snapshots
- explicit benchmark/model/retriever/prompt configuration retention
- continue-on-error execution by default
- explicit stop-on-error mode
- question-level result retention
- batch error retention
- aggregate evaluation reporting
- failure retention through the existing V3/V4 failure records

## Experiment identity

The existing Experiment.create() contract remains the source of experiment identity. Its ID is derived from the experiment name, description, model configuration, embedding configuration, retriever configuration, top-k, prompt version, and benchmark version.

The batch engine additionally records a serializable configuration snapshot.

## Batch semantics

A batch:

1. receives one explicit experiment configuration
2. receives a fixed question list
3. validates unique question IDs
4. executes questions in supplied order
5. retains successful results
6. retains execution errors
7. optionally stops at the first error
8. returns aggregate execution counts

A failed question does not erase successful results.

## Reporting

Batch reports combine:

- experiment configuration
- requested/completed/failed counts
- success rate
- aggregate evaluation metrics
- recorded classifier failures
- batch execution errors

No composite quality score is introduced.

## Failure retention

Failures produced by the existing V3 failure workflow remain attached to ExperimentResult.failures and can be supplied to the batch report.

Execution errors are retained separately so infrastructure/provider failures are not confused with evaluated clinical-answer failures.

## Reproducibility boundary

Reproducibility requires keeping the following fixed:

- benchmark version
- question IDs/order
- controlled corpus
- model configuration
- embedding configuration
- retriever configuration
- top-k
- prompt version
- evaluator versions

The engine does not claim deterministic model outputs for stochastic external providers.

## Limitations

- Actual batch execution still depends on the configured model/provider environment.
- No distributed scheduling is introduced.
- No parallel execution is introduced; sequential execution preserves simple ordering and failure behavior.
- Statistical comparison is deferred to V5.6.

## Verification

Focused unit coverage was added for batch execution, error retention, stop-on-error behavior, configuration snapshots, and batch reporting.

No empirical benchmark result is claimed until a batch is actually executed.
